# Schemas are authored inline and enum-free, with optionality as nullable unions and only dates and money normalized

Designing the Hungarian ID card / passport / driving licence / address card / NAV-compatible invoice Schemas (#34) forced four cross-cutting authoring rules that a reader of the Schema files alone would find arbitrary, because their justification lives in how the extraction tool is built rather than in the Schemas themselves. `_extraction_tool` (`model_provider/anthropic_provider.py`) copies each *top-level property's* subschema verbatim into a per-Field `{value, confidence}` wrapper — so the Schema the Model Provider sees is not the Schema `jsonschema` validates against, and the two disagree in ways that decide whether a legitimate document extracts or fails.

**Amended by #45.** The tool used to mark **every** top-level Field `required`, regardless of the Schema's own `required` list; it now propagates that list through, so a Field the Schema leaves optional can be omitted from the tool call. Two of the rules below were founded on the old behaviour and are restated here on the grounds that survive it — the conventions themselves are unchanged, and no committed Schema needed editing.

We chose, for every Schema in the Registry:

- **No `$ref`/`$defs` — nested structures are inlined.** A sibling `$defs` block at the Schema root is not carried into the extraction tool, so a `$ref` inside a property dangles there while still resolving during validation. The breakage is silent and asymmetric, and the deduplication `$defs` buys isn't worth it at Registry scale.
- **Optionality is a nullable union (`["string", "null"]`), and the Field is also left out of `required`.** The union is the load-bearing half: it makes "not on this document" an explicit, validating, Confidence-carrying extracted value rather than a missing row, consistent with this project's preference for explicit outcomes over silent defaults (ADR-0004's no-system-wide-default, `unclassified` as an explicit result). Before #45 it was also the only way to survive Extraction at all — the tool forced every Field present, so a Field the document genuinely lacks came back as `null` against a bare `"type": "string"`, costing a retry then `extraction_failed`. That pressure is gone; the union stays on its own merits, and omitting the Field from `required` is now what makes the escape hatch real for a Schema whose optional Field *isn't* nullable (`invoice/v1`'s `invoiceDate`, immutable under ADR-0007 and so unfixable by editing). `null` remains the intended spelling of absence — the extraction prompt asks for it wherever the Field's type admits it — and omission is tolerated, not preferred.
- **`required` lists only Fields the document genuinely always prints** — it is now enforced in both places it appears, so it must be honest about the documents rather than aspirational about the data. During Extraction the tool propagates it (#45): a Field listed there and then not emitted is a validation error, a retry, and on a second failure `extraction_failed`. It is equally enforced against a Review submission (`resolve_extraction` validates the caller's own Field set), where a missing Field is terminal — `extraction_failed`, with no retry. Inside an array-of-object Field a different rule holds: the nested subschema is copied verbatim into the tool and validated as-is, and nested `required` therefore lists **every** nested property while **every** nested property is a nullable union — `required` then guarantees the row's shape and `null` carries absence, which makes a content-driven `extraction_failed` impossible while still denying "key absent" and "value null" two spellings of the same fact.
- **No `enum`, ever — constrained vocabularies go in the `description`.** The model sees `description` either way, so guidance is not lost; what changes is the failure mode. An `enum` is validated, so a value outside it fails the document hard, and ADR-0007 immutability means correcting the list requires minting a new Schema version. Real documents defeated every enum we considered: ICAO 9303 specifies the passport's `sex` field as a *national* initial (a Hungarian passport can print `N/F` for *nő*), which an obvious `["M","F","X"]` would reject. An unexpected value should mean low Confidence and a Review, never `extraction_failed`.
- **Only dates and monetary amounts are normalized; everything else is transcribed verbatim.** Dates become ISO `YYYY-MM-DD` (`"format": "date"`) with the *printed* format named in the `description`, and amounts become JSON numbers with separators and currency symbols stripped — a Hungarian invoice prints `1 234 567,89 Ft`, and a driving licence prints category dates as `DD.MM.YY`. Everything else — names (accents intact), document numbers, category and restriction codes, MRZ characters — is captured exactly as printed, because Extraction is transcription and normalization is the caller's job.

## Consequences

- Two-digit printed years require the model to infer a century, and its Confidence reflects how well it *read* the characters, not how sure it is of the century it supplied — so a wrong century can arrive above the Confidence Threshold. Accepted deliberately: a caller checking whether a licence category is still valid needs a comparable date, and pushing three printed date formats onto every consumer defeats the point. Mitigated by naming the century rule in the `description`.
- `format` is annotation-only: `extraction_validation_errors` builds its validator without a `format_checker`, so `"format": "date"` guides the model but never fails a Document. A model that emits a printed-form date degrades to a readable string rather than an `extraction_failed`.
- Nullable unions mean a `fields` row is *expected* for every Field of every extracted Document, including known-absent ones, and consumers distinguish "absent from the document" (`null`) from "not part of this Document Type" (no row) — they are different facts. Since #45 that expectation is a prompt-level nudge rather than a schema-level guarantee: an optional Field the model omits outright validates fine and leaves no row, collapsing the two facts for that Field. Accepted rather than closed off by listing every Field in top-level `required`, which would restore a content-driven `extraction_failed` for exactly the documents the nullable-union rule exists to protect.
- A Schema's top-level `required` list now decides real Extraction outcomes, so over-listing is no longer free: a Field listed there that some legitimate document doesn't print costs that Document a retry and then `extraction_failed`, where before #45 the same mistake stayed invisible until a caller resolving a Review handed back an honest Field set. The list gets tighter scrutiny than it did, and the failure it produces is louder and earlier.

# Schemas are authored inline and enum-free, with optionality as nullable unions and only dates and money normalized

Designing the Hungarian ID card / passport / driving licence / address card / NAV-compatible invoice Schemas (#34) forced four cross-cutting authoring rules that a reader of the Schema files alone would find arbitrary, because their justification lives in how the extraction tool is built rather than in the Schemas themselves. `_extraction_tool` (`model_provider/anthropic_provider.py`) copies each *top-level property's* subschema verbatim into a per-Field `{value, confidence}` wrapper and marks **every** Field `required`, regardless of the Schema's own `required` list — so the Schema the Model Provider sees is not the Schema `jsonschema` validates against, and the two disagree in ways that decide whether a legitimate document extracts or fails.

We chose, for every Schema in the Registry:

- **No `$ref`/`$defs` — nested structures are inlined.** A sibling `$defs` block at the Schema root is not carried into the extraction tool, so a `$ref` inside a property dangles there while still resolving during validation. The breakage is silent and asymmetric, and the deduplication `$defs` buys isn't worth it at Registry scale.
- **Optionality is a nullable union (`["string", "null"]`), not omission from `required`.** Because the tool forces every Field present, a Field the document genuinely lacks is emitted anyway — as `null`, which fails a bare `"type": "string"` and costs a retry then `extraction_failed`. Typing it as a union makes "not on this document" an explicit, validating, Confidence-carrying extracted value, consistent with this project's preference for explicit outcomes over silent defaults (ADR-0004's no-system-wide-default, `unclassified` as an explicit result).
- **No `enum`, ever — constrained vocabularies go in the `description`.** The model sees `description` either way, so guidance is not lost; what changes is the failure mode. An `enum` is validated, so a value outside it fails the document hard, and ADR-0007 immutability means correcting the list requires minting a new Schema version. Real documents defeated every enum we considered: ICAO 9303 specifies the passport's `sex` field as a *national* initial (a Hungarian passport can print `N/F` for *nő*), which an obvious `["M","F","X"]` would reject. An unexpected value should mean low Confidence and a Review, never `extraction_failed`.
- **Only dates and monetary amounts are normalized; everything else is transcribed verbatim.** Dates become ISO `YYYY-MM-DD` (`"format": "date"`) with the *printed* format named in the `description`, and amounts become JSON numbers with separators and currency symbols stripped — a Hungarian invoice prints `1 234 567,89 Ft`, and a driving licence prints category dates as `DD.MM.YY`. Everything else — names (accents intact), document numbers, category and restriction codes, MRZ characters — is captured exactly as printed, because Extraction is transcription and normalization is the caller's job.

## Consequences

- Two-digit printed years require the model to infer a century, and its Confidence reflects how well it *read* the characters, not how sure it is of the century it supplied — so a wrong century can arrive above the Confidence Threshold. Accepted deliberately: a caller checking whether a licence category is still valid needs a comparable date, and pushing three printed date formats onto every consumer defeats the point. Mitigated by naming the century rule in the `description`.
- `format` is annotation-only: `extraction_validation_errors` builds its validator without a `format_checker`, so `"format": "date"` guides the model but never fails a Document. A model that emits a printed-form date degrades to a readable string rather than an `extraction_failed`.
- Nullable unions mean a `fields` row exists for every Field of every extracted Document, including known-absent ones. Consumers distinguish "absent from the document" (`null`) from "not part of this Document Type" (no row) — they are different facts.
- Propagating a Schema's own `required` into the extraction tool would remove the need for the nullable-union rule. That's a pipeline change, not a Schema authoring convention, and is tracked separately.
